Էրեբունու պահանջագրի, տեղափոխման, վերադարձի և գույքագրման ձևերը բացվել են, ստուգվել և չեղարկվել։ Գործողության կամ աղբյուրի մասնաճյուղը սահմանափակված է սեփական տեղանքով, իսկ տեղափոխման ստացողները ներառում են մյուս ակտիվ պահեստները։ Արտադրական պահեստային փաստաթուղթ չի ստեղծվել, հաստատվել, չեղարկվել կամ հակադարձվել ստուգման նպատակով։

## Հայտնաբերված և ուղղված խնդիրներ

1. **Մասնաճյուղը չէր կարող ընտրել տեղափոխման ստացողին։** `catalog/transfers/options`-ը վերադարձնում էր միայն սեփական մասնաճյուղը, իսկ ձևը այդ նույն մասնաճյուղը բացառում էր ստացողների ցանկից։ Այժմ տեղափոխման համար վերադարձվում են բոլոր ակտիվ պահեստների միայն ID/անուն/կոդ դաշտերը։ Պահանջագրի և մնացորդի տարբերակները շարունակում են սահմանափակվել սեփական մասնաճյուղով։ Կենդանի Էրեբունու ձևում հաստատվել են Գյումրի, Շենգավիթ և Կենտրոնական պահեստ տարբերակները, ընտրվել է Գյումրին, ձևը չեղարկվել է։
2. **Տեղափոխման էջը կենտրոնական admin-ին առաջարկում էր այլ մասնաճյուղի ստացման գործողություն։** Ստացման կոճակն այժմ հասանելի է միայն փաստացի ստացող մասնաճյուղի աշխատակցին՝ համապատասխան խմբագրման իրավունքով։ Ուղարկումը և աղբյուրի ընտրությունը նույնպես հետևում են իրական տեղանքին, այդ թվում մասնաճյուղին կցված admin դերի դեպքում։
3. **Գույքագրումը սկսած աշխատակցին առաջարկվում էր սեփական հաշվարկի անկախ հաստատում։** Կոճակն ու գործողության handler-ը հիմա կիրառում են նույն անկախ հաստատման սահմանափակումը, ինչ backend-ը։
4. **Տեղափոխման ցանկում բացակայում էին արտահանման կոճակները։** Ավելացվել են CSV/Excel՝ `transfers.export` իրավունքով և ընթացիկ որոնման/ֆիլտրերի փոխանցմամբ։

Manager-ի տրամադրված գաղտնաբառը սկզբում մերժվել է։ Օգտատիրոջ հստակ հանձնարարությամբ այն փոխարինվել է նրա տրամադրած արժեքով՝ հավելվածի `setPlainPassword` մեթոդով։ Hash-ի ստուգումն ու հետագա իրական մուտքը հաջող են։ ID-ն, դերը, մասնաճյուղն ու ակտիվությունը չեն փոխվել։ SSH մուտքերը պահպանված են ըստ նախորդ հանձնարարության։

## Արտադրական API ստուգում

Տեղադրված `2bb61e5` տարբերակի սերվերի HTTP kernel-ով իրական route-երի վրա կատարվել է **96 ստուգում՝ 24 յուրաքանչյուր իրական հաշվի համար, բոլորն անցել են**։ Հաշվի դերերն ու մասնաճյուղը կարդացվել են production բազայից։ Մուտքերն առանձին հաստատվել են իրական բրաուզերում. API ստուգման ընթացքը նոր token չի ստեղծել և գաղտնաբառ չի կարդացել։

Ստուգվել են 14 page route, մատակարարների ցանկը, ընթացիկ օգտատերը, վահանակը, ծանուցումները, մնացորդների մատրիցան, տեղափոխման տարբերակները և մնացորդների հաշվետվությունը։ **13 սպասված permission մերժումը վերադարձրել է `403`**։ Տեղափոխման տարբերակներում բոլոր հաշիվների համար վերադարձվել են ակտիվ պահեստների միայն ID/անուն/կոդ դաշտերը։ Էրեբունու հաշվետվությունը նույնիսկ `branch_id=0` պարտադրելու դեպքում մնացել է Էրեբունու սահմանում՝ առանց արժեքների։

Յուրաքանչյուր հաշվով արտահանվել է մեկ մնացորդային հաշվետվություն CSV, XLSX և PDF ձևաչափերով՝ **12 հաջող պատասխան**։ Ստուգվել են UTF-8 BOM, ZIP/XLSX և `%PDF-` սկզբնական ստորագրությունները և ոչ դատարկ բովանդակությունը։ Տվյալները մնացել են միայն սերվերի գործընթացի հիշողությունում. հաշվետվության բովանդակություն չի արտածվել կամ պահպանվել որպես audit ապացույց։

Բազայի հարցումների guard-ը մերժում էր ցանկացած գործողություն, որը չէր սկսվում `SELECT`, `SHOW`, `DESCRIBE` կամ `EXPLAIN` բառով։ Նույն **18 աշխատանքային աղյուսակի քանակն ու ամբողջ բովանդակության hash-ը API ստուգումից առաջ և հետո նույնն են**։

## Գործնական սահմաններ

Իրական էջերը ստուգվել են ներկա տվյալներով։ Գնումների, տեղափոխումների և գույքագրումների դատարկ ցանկերը չեն ծածկում բոլոր աշխատանքային վիճակները. այդ անցումները և մերժումների ազդեցությունը ստուգվել են մեկուսացված API/component թեստերով։ Բրաուզերի CSV սեղմման download event-ը գործիքով չի հաստատվել. ձևաչափերի ապացույցը վերը նկարագրված production API արտահանումն է։ Արտադրական 96 հարցումները առանձին բոլոր 19 հաշվետվության տեսակների ամբողջական matrix չեն։ Մեծ բեռնվածության, միաժամանակյա MySQL մրցակցային գործարքների և ֆիզիկական տպիչի/սկաների/տեսախցիկի փորձարկում այս փուլում չի կատարվել։
